# Brytenwalda — how its AI actually works

**Question answered**: the repo owner played *Brytenwalda* and reports its AI
"runs quite well". Our prior research (`ai-research-2026-08/brief-04-amai.md`
§9) recorded it as one of only two counterexamples to "no WC3 AI handles real
geography", with competence **UNKNOWN** — no source, benchmark or replay. This
file reads the shipped artifact and answers *how*.

**Decomposition date**: 2026-08-12.
**Artifact**: `Brytenwalda 1.37a.w3x`, 23,704,226 bytes, by **ChasLycan,
Delinard** (w3i author field), obtained from Hive Workshop resource 88357 /
thread 287147. Extracted to a scratchpad, read, and **not committed** — gotcha
9 and the Legal section. Nothing in this file is copied content; quotes are
short illustrative snippets from a decompiled `war3map.j` and an engine `.ai`
script.

## Evidence classes

Same ledger as `ai-research-2026-08/`:

- **DOCUMENTED** — stated by the map's own resource page, changelog or author post.
- **CODE-INFERRED** — follows from the shipped `war3map.j` / `.ai` / object data read here, not verified in a running match.
- **EXPERIMENTAL** — observed in play.
- **FOLKLORE** — community claim without reproducible detail.
- **UNKNOWN** — no adequate evidence located.
- **NEGATIVE SEARCH** — looked for, not found; not proof of absence.

The one **EXPERIMENTAL** input is the repo owner's playtest verdict ("runs
quite well"). Everything else below is **CODE-INFERRED** unless labelled.

## Executive verdict

| Question | Answer | Evidence |
|---|---|---|
| Which architecture? | **Hybrid, and the engine `.ai` path is real.** One World-Editor-generated `.ai` script (`war3mapImported\Brytenwalda AI.ai`, 2,720 lines) started via `StartCampaignAI` for every computer slot, plus a map-script diplomacy layer that decides *who* each AI fights. | CODE-INFERRED |
| Does it use `MAP_CONTROL_COMPUTER`? | Yes, and it **reads** rather than converts. 19 of 21 slots are declared *User* in the w3i; the host sets them to Computer in the lobby; the map derives its AI roster from `GetPlayersByMapControl(MAP_CONTROL_COMPUTER)`. | CODE-INFERRED + DOCUMENTED (author: "Mostly because how setting several slots to computer actually affects some stuff") |
| How does it choose objectives? | **Two layers.** Strategic: a hand-authored 19-node **adjacency table** (`PG_PotentialEnemies`, 49 directed edges) + a random neighbour draw every 45 s, gated on army size and gold. Tactical: the strategic layer sets the alliance graph, then the engine natives `GetEnemyExpansion()` / `GetEnemyBase()` pick the actual building to hit. There is **no route model, no chokepoint model and no region graph** anywhere. | CODE-INFERRED |
| How does it move armies? | One `AttackMoveKillA(target)` per wave, to the engine captain, after `FormGroup(3, true)`. **Exactly one order site in the whole AI.** No per-unit orders, no waypoints, no re-issue loop. | CODE-INFERRED |
| Does it cheat? | **Yes, in three specific and quantifiable places** — a large recurring lumber subsidy (+250 lumber / 45 s), a free movement-speed upgrade humans must buy (and a higher cap), and hero XP handicaps of 150–500%. Gold income is *symmetric*. No vision cheat found. | CODE-INFERRED |
| Does it commit partially? | **No — it always commits everything.** The assault group is `min = max = all` of every combat unit type the faction can own. There is no reserve, no garrison, no split. | CODE-INFERRED |
| Why does it read as competent? | Because the **map** removes almost every hard case before the AI meets it: buildings cannot be placed (only upgraded in place on pre-placed plots), gold needs no harvesting, the one sea crossing is a waygate, and the AI is *forbidden* to close gates. | CODE-INFERRED |

**One-line architecture verdict**: Brytenwalda is a *thin* engine-`.ai`
tactical layer under a *thick* map-script diplomacy layer, and it is competent
not because it solves geography but because the map was designed so that
geography never becomes the AI's problem.

## 1. The artifact and how it boots

Extraction (`tools/w3x-extract.js --recover-names`) yields 370 members. The
relevant ones:

| Member | Size | Role |
|---|---:|---|
| `war3map.j` | 2,010,199 B | map script (decompiled GUI; 162 triggers) |
| `war3mapImported/Brytenwalda AI.ai` | 131,390 B / 2,720 lines | **the AI**, one file, shared by every AI faction |
| `war3map.w3u` | 214,818 B | object data (751 named units/upgrades/abilities resolved) |

The `.ai` header says `Generated by the Warcraft III World Editor` — it is **AI
Editor output**, not hand-written JASS. That matters: the whole thing is the
stock WE AI template (`InitOptions` / `UpdateConditions` / `BuildPriorities` /
`HaveMinimumAttackers` / `PrepareAttackGroup` / `LaunchAttack` /
`AttackAssignment` / `main`) with the data slots filled in. The author wrote
*tables*, not control flow.

Boot path (`war3map.j`):

```jass
// InitTrig_SetupAI — a single one-shot timer at t = 6 s
call TriggerRegisterTimerEventSingle(gg_trg_SetupAI, 6.00)
...
// Trig_SetupAI_Actions:  ForForce(udg_PG_Kingdoms_AI, function Trig_SetupAI_Func001A)
// Trig_SetupAI_Func001A, per AI player (line 23959):
    ... ~30 tech/ability/handicap adjustments ...
    call StartCampaignAI(GetEnumPlayer(), "war3mapImported\\Brytenwalda AI.ai")   // :23995
    call RemoveAllGuardPositions(GetEnumPlayer())                                 // :23996
```

Three things worth naming:

1. **`StartCampaignAI`, not `StartMeleeAI`.** `InitOptions` confirms it with
   `SetCampaignAI()`. The engine's melee campaign (expansion hunting, creeping,
   tech-tree racing) is off; what remains is build-order execution + assault
   waves. On a territorial map that is the right half of the engine to keep.
2. **`RemoveAllGuardPositions` immediately after the start.** This is the
   handoff `brief-03-captains.md` predicted would be needed: preplaced garrison
   units are released from guard duty so the captain may recruit them. Without
   it, ~2,980 preplaced units would sit still. It is done once, at boot, and
   never revisited.
3. **The AI roster is derived, not declared.**
   ```jass
   call ForForce(GetPlayersByMapControl(MAP_CONTROL_COMPUTER), function Trig_SetupMapInitialization_Func390A)
   // Func390A: ForceAddPlayerSimple(GetEnumPlayer(), udg_PG_Kingdoms_AI)  (+ removes 4 scripted specials)
   ```
   The w3i declares 19 slots as **User** and only players 15 and 21 as
   Computer; the remaining AI slots exist because the *host* set them to
   Computer in the lobby. Brytenwalda therefore never needs the runtime
   controller conversion our own bootstrap relies on — it takes the supported
   path and simply reads `GetPlayerController`.

The Viking invader (Player 6) gets the same `.ai` on a separate, event-driven
trigger (`war3map.j:35224`), also followed by `RemoveAllGuardPositions`.

## 2. The `.ai` layer, in full

The whole tactical AI is ~120 lines of logic wrapped around ~2,300 lines of
generated tables. Here is `main` verbatim:

```jass
function main takes nothing returns nothing
    call InitAI(  )
    call InitOptions(  )
    call SelectHeroes(  )
    call CreateCaptains(  )
    call SetHeroLevels( function ChooseHeroSkill )
    call Sleep( 0.1 )
    call StartThread( function WorkerAssignment )
    call StartThread( function AttackAssignment )
    call PlayGame(  )
endfunction
```

Two threads. That is the entire concurrency model.

### 2.1 Options — what the engine is told to do

```jass
call SetCampaignAI()          call SetDefendPlayer( false )
call SetRandomPaths( false )  call SetTargetHeroes( false )
call SetPeonsRepair( true )   call SetHeroesFlee( true )
call SetHeroesBuyItems(false) call SetUnitsFlee( false )
call SetGroupsFlee( true )    call SetWatchMegaTargets( false )
call SetIgnoreInjured(false)  call SetHeroesTakeItems( false )
call SetSlowChopping( false ) call SetCaptainChanges( true )
call SetSmartArtillery( true )
```

Read as design intent: **groups flee but individual units do not**
(`SetGroupsFlee(true)` / `SetUnitsFlee(false)`) — the army retreats as a body
rather than dissolving; **heroes flee** and are excluded from item and
targeting logic; **`SetRandomPaths(false)`** — take the direct route, do not
wander; **`SetDefendPlayer(false)`** — do not defend allies.

### 2.2 The attack loop

```jass
function AttackAssignment takes nothing returns nothing
    call StaggerSleep( 0, 2 )
    if (attackWave == 1) then
        call AttackWaveDelay( 0 )         // Sleep(30) at game start
    endif
    loop
        loop
            call UpdateConditions(  )
            exitwhen (HaveMinimumAttackers() and not CaptainRetreating())
            call Sleep( 2 )
        endloop
        call RemoveInjuries(  )
        call ResetAttackUnits(  )
        call PrepareForces(  )
        call LaunchAttack(  )
    endloop
endfunction
```

- `StaggerSleep(0, 2)` — the only concurrency control between the up-to-19
  simultaneous AI players. Randomised phase offset so their expensive frames
  do not align.
- The wait condition is `HaveMinimumAttackers() and not CaptainRetreating()`.
  **`CaptainRetreating()` is the entire failure-recovery mechanism**: a beaten
  army retreats under engine control, and the AI simply refuses to start a new
  attack until it stops retreating. There is no blacklist, no write-off, no
  memory that the last attack failed.
- `RemoveInjuries()` — wounded units are pulled from the wave.
- Polling cadence: 2 s, plus a 20 s inter-wave delay.

### 2.3 Force composition — total commitment

`PrepareAttackGroup(1)` is ~200 lines of exactly this shape, once per combat
unit type (~90 types):

```jass
set all = GetUnitCountDone( 'h06L' )
call AddAttackUnit( all, all, 'h06L' )
```

`min = max = all`. **Every unit the faction owns joins every wave.** There is
one attack group (its name in the AI Editor is still the template default,
`CrushThesePeasants`), one wave, and `AttackWaveUpdate` resets `attackWave` to
1 forever, so the wave never escalates or varies — it just repeats.

This is the single most consequential design decision in the file, and it is
the direct answer to two of our five failures. Brytenwalda's armies never fail
to commit fully, because *partial commitment is not representable*. It also
means the AI has no home garrison at all, which is handled elsewhere (§2.4).

### 2.4 Target selection

```jass
function LaunchAttack takes nothing returns nothing
    local unit target = null
    // Don't launch any attack while town is threatened
    if (TownThreatened()) then
        call Sleep( 2 )
        return
    endif
    if (( ( FoodUsed() > 35 ) and ( GetUnitCountDone( 'h04Y' ) > 0 ) )) then
        if (target == null) then
            set target = GetEnemyExpansion()
            if (target == null) then
                call StartGetEnemyBase(  )
                loop
                    exitwhen (not WaitGetEnemyBase())
                    call SuicideSleep( 1 )
                endloop
                set target = GetEnemyBase()
            endif
        endif
    endif
    if (( FoodUsed() > 25 )) then
        ... identical block ...
    endif
    if (target != null) then
        call AttackTarget( target, setAlly )
        call AttackWaveUpdate(  )
    else
        call Sleep( 20 )
    endif
endfunction
```

Everything about geography is inside `GetEnemyExpansion()` and
`GetEnemyBase()` — **Blizzard's hardcoded natives**. The map contributes
nothing to *which building* gets attacked. The two "target priorities" the AI
Editor exposes are set to the same expression at two different food thresholds,
so in practice the rule is: *at 25 food, hit the nearest enemy expansion, else
the enemy base.*

`TownThreatened()` is the defence policy: **when home is under attack, do not
attack.** Combined with total commitment, the AI's behaviour is a clean
two-state machine — everything is either at home (because home is threatened)
or in the field (because it is not).

### 2.5 The move order

```jass
function AttackTarget takes unit target, boolean addAlliance returns nothing
    if (target == null) then
        return
    endif
    if (addAlliance) then
        call SetAllianceTarget( target )
    endif
    call FormGroup( 3, true )
    call AttackMoveKillA( target )
    ...
endfunction
```

Three calls, and the important counts across the whole 2,720-line file:

| Primitive | Occurrences |
|---|---:|
| `AttackMoveKillA` | **1** |
| `FormGroup` | **1** |
| `SetAllianceTarget` | 2 |
| `IssuePointOrder`-family (per-unit) | **0** |

**Order volume is one order per wave, per AI player, roughly every 20+ seconds
plus travel time.** That is on the order of 1–3 orders per minute for the
entire 19-faction world. Our order-spam/unit-lag bug is structurally
impossible here.

`FormGroup(3, true)` before moving is the anti-trickle mechanism: the army
gathers at a staging point before it sets off, so it arrives as a body rather
than in a stream. `SetAllianceTarget(target)` is how allied AIs coordinate —
the engine shares the chosen target across the alliance so allies converge on
the same building instead of picking their own.

### 2.6 Economy — deliberately vestigial

```jass
function HarvestPriorities takes nothing returns nothing
    local integer mine = TownWithMine()
    local integer allGold = GetUnitCountDone('h069')
    local integer allWood = GetUnitCountDone('h069')
    local integer numWorkers
    set numWorkers = allWood
    if (numWorkers > 0) then
        call HarvestWood( 0, numWorkers )
    endif
endfunction
```

`mine` and `allGold` are computed and never used. **`HarvestGold` is called
zero times in the file.** Every Serf chops wood; nobody mines. Gold comes
entirely from the map's territory income system (§3.3), which is symmetric with
the human's.

Build primitive counts:

| Primitive | Occurrences |
|---|---:|
| `SetBuildAll(BUILD_UNIT, …)` | 1,514 |
| `SetBuildAll(BUILD_UPGRADE, …)` | 53 |
| `SetBuildAll(BUILD_STRUCTURE, …)` | **0** |
| `BUILD_EXPANSION` | **0** |
| `SetBuildExpa` | 1 (inside `BuildExpansion`, which is **never called**) |

The build order is a flat list of `if (FoodUsed() > N) then SetBuildAll(...)`
rules — a pure train/research queue keyed on army size, with faction identity
supplied by 40 `gCond_*` booleans recomputed every 2 s from the player's own
culture upgrades:

```jass
set gCond_BuildingsAngle = ( ( GetUpgradeLevel( 'R012' ) == 1 ) and ( GetUnitCount( 'h02G' ) > 0 ) )
set gCond_UnitsWelshFootmen = ( ( GetUnitCount( 'h00J' ) > 0 ) and ( GetUpgradeLevel( 'R000' ) == 1 ) )
```

**One script serves 19 factions**, differentiated only by which upgrade-gated
conditions are true for the player running it. That is a genuinely good idea and
costs nothing.

### 2.7 Heroes — not attempted

```jass
function SetHero takes integer order, integer heroid returns nothing
endfunction

function SelectHeroes takes nothing returns nothing
    local integer roll = GetRandomInt(1,100)
    if (roll <= 17) then
    elseif (roll <= 34) then
    ...
    endif
endfunction
```

Empty. `ChooseHeroSkill` indexes `skills1/2/3[]` arrays that are never
populated, so it returns 0. Hero selection and skill choice are left entirely
to the engine defaults; the map compensates with a hard-coded
`SelectHeroSkill(GetTriggerUnit(), 'A022')` on every AI hero level-up
(`Trig_AILevelUp_Actions`) and with scripted skill lists for named heroes.

## 3. The map layer — where the "strategy" lives

### 3.1 The geography model is a hand-authored adjacency table

`war3map.j:7313–7370` initialises, per player, the set of players it is
allowed to want war with:

```jass
call ForceAddPlayerSimple(Player(3),  udg_PG_PotentialEnemies[1])
call ForceAddPlayerSimple(Player(4),  udg_PG_PotentialEnemies[1])
call ForceAddPlayerSimple(Player(7),  udg_PG_PotentialEnemies[1])
call ForceAddPlayerSimple(Player(11), udg_PG_PotentialEnemies[1])
call ForceAddPlayerSimple(Player(21), udg_PG_PotentialEnemies[1])
```

Measured over the block:

| Property | Value |
|---|---|
| Nodes (players with a neighbour list) | 19 |
| Directed edges | 49 |
| Mean out-degree | 2.58 |
| Degree range | 1 – 5 |
| Reciprocated edge-ends | 40 of 49 |

This **is** a geography model — it encodes who borders whom on Britain and
Ireland — but it is *static, coarse and hand-drawn*. It has no notion of
distance, route, crossing, chokepoint or cost. It is a list of legal wars,
not a map.

It is also nearly the only place geography appears, and it is mutated in
exactly three ways: diplomacy (peace returns an enemy to the potential list),
kingdom formation, and the Irish Strait research (§3.4).

### 3.2 The strategic tick

`udg_Income` is a repeating **45-second** timer (`war3map.j:8065`). It drives
`FunctionPlayerCycle`, a fully unrolled per-player pass:

```jass
call TriggerSleepAction(0.01)
set udg_Temp_Player1 = Player(0)
set udg_Temp_Player2 = ForcePickRandomPlayer(udg_PG_PotentialEnemies[GetConvertedPlayerId(udg_Temp_Player1)])
...
call TriggerExecute(gg_trg_AIWarPeace)
// repeated verbatim for every player
```

**The war target is drawn uniformly at random from the neighbour list.** There
is no scoring, no weakness detection, no value model, no opportunism. The only
intelligence is in the *gates* around the draw (`Trig_AIWarPeace_Func001Func003C`):

```jass
if ( not Trig_AIWarPeace_Func001Func003Func001C() ) then return false endif   // has 0 enemies, or is a vassal
if ( not ( CountPlayersInForceBJ(udg_PG_PotentialEnemies[...]) >= 1 ) ) then return false endif
if ( not ( GetPlayerState(udg_Temp_Player1, PLAYER_STATE_RESOURCE_FOOD_USED) >= 25 ) ) then return false endif
if ( not ( GetPlayerState(udg_Temp_Player1, PLAYER_STATE_RESOURCE_GOLD)      >= 100 ) ) then return false endif
```

Note the coupling, which is the cleverest thing in the map: the war gate is
**FoodUsed ≥ 25**, and the `.ai`'s attack gate is **FoodUsed > 25**. *A
Brytenwalda AI only declares war when it already has the army that will
immediately march.* That single shared constant is why factions never sit at
home in a war they are not prosecuting — the failure our AI hits as "factions
that never leave home."

Further hysteresis: a war may not be declared against a player you *recently
made peace with* (`P_AI_RecentPeace`), and peace is only offered on a 1-in-5
roll per tick, with a 1-in-6 roll to clear the recent-peace memory. Coarse, but
it prevents war/peace flapping.

The AI also declares war **reactively**: `AISuddenWar` fires on being attacked
and immediately makes the attacker an enemy, dragging in both sides' vassals.

Everything else in `AIWarPeace` (189 lines) is alliance bookkeeping: vassals
follow their overlord into war, tributaries pay, revolts break subject status.
`CM_NeutralAI` (80 lines) is the AI's negotiation interface with the human —
envoys, gold demands, peace offers and 9 randomised flavour replies. A large
fraction of the felt "intelligence" of this map is diplomacy the player can
*talk to*, not army handling.

### 3.3 Income is symmetric

`FunctionIncomeExpire` pays every player, human and AI alike, from the same
`udg_PlayerGold[]` territory accumulator (per-settlement values summed at
init; observed range **18–213 gold per 45 s tick**), with the same vassal
(÷3) and tributary (÷6) tax splits. **No asymmetry.** Gold — the resource the
map's own systems handle — is fair.

### 3.4 Water: the crossing is a waygate, not a transport problem

The `.ai` has no transport logic whatsoever (0 references to loading, boats or
embarkation). Britain and Ireland are separate landmasses. The changelog line
our prior brief cited as evidence of geography-aware authoring — *"Fixed Irish
AI not invading mainland"* (v1.34d, **DOCUMENTED**) — resolves to this:

```jass
function Trig_ResearchIrishStrait_Actions takes nothing returns nothing
    set udg_EventIrishStrait = true
    call WaygateActivateBJ(true, gg_unit_n00C_0779)
    call WaygateActivateBJ(true, gg_unit_n00C_0667)
    call ShowUnitShow(gg_unit_n00C_0779)
    call ShowUnitShow(gg_unit_n00C_0667)
    if ( Trig_ResearchIrishStrait_Func008C() ) then          // GetPlayerController(...) == MAP_CONTROL_COMPUTER
        ... ForGroup: ForceAddPlayerSimple(owner, udg_PG_PotentialEnemies[3 or 19]) ...
    endif
```

A **research (`R018`, "Establish Irish Strait")** activates a pair of waygates
and simultaneously **adds edges to the adjacency graph**. After that, the Irish
Sea is an ordinary pathable link: `AttackMoveKillA` walks an army across it with
no transport code, and the strategic layer knows new wars are legal.

This is the cleanest example of the map's whole method. The hardest geographic
case in the map — an amphibious invasion — was not solved in the AI. It was
**deleted from the terrain**, gated behind a tech so it still reads as a
strategic milestone, and paid for with two graph edges. There is exactly one
waygate pair in the map.

### 3.5 Buildings cannot be placed — by anyone

This is the finding that most explains the AI's competence, and it is airtight
in the object data. Across every unit in the map, only **three** have a build
list at all:

| Builder | `ubui` (can construct) |
|---|---|
| `h069` Serf | `h06S` (The Wonder) |
| `h0CD` Thrall (Viking) | `h06S`, + 4 Norse structures |
| `e001` Trade Caravan | `o002` |

No barracks, tower, workshop or military structure is directly constructible.
They exist only as **in-place upgrades of pre-placed plots**:

```
h02G "Military Building Location"  uupt → h04Y,h053,h015,h022,h003,h008,h00J,h00L,h01B,h08B,h01F,h04C
h0AA "Military Building Location"  uupt → h0BO,h07W,h07O,h09T
h02I "Tower Building Location"     uupt → o006,h08S
h02H "Workshop Building Location"  uupt → h009
```

The author hand-placed empty building plots at sensible, terrain-appropriate
positions across a 222×253 map, and every faction — human and AI — "builds" by
upgrading a plot in place. **There is no building-placement problem in this
map.** The classic custom-map AI failure (walling itself in, blocking its own
ramp, placing a barracks in a lake) cannot occur. That is why the `.ai` can get
away with emitting structure IDs through `BUILD_UNIT` and never touching
`BUILD_STRUCTURE` or `BUILD_EXPANSION`.

### 3.6 Gates: the AI is forbidden to close them

The map has gates as units (`h04M`/`h04N`/`h052`/`h0E6`/`h0EA` "Wooden Gate")
with `A05Y` Open Gate and `A05X` Close Gate abilities (both `Absk`-based, 60 s
cooldown). In the AI setup block (`war3map.j:23959–23996`):

```jass
call SetPlayerAbilityAvailableBJ(false, 'A05X', GetEnumPlayer())   // :23965  Close Gate — DISABLED for AI
call SetPlayerAbilityAvailableBJ(false, 'A00J', GetEnumPlayer())   // Defend
call SetPlayerAbilityAvailableBJ(false, 'A03J', GetEnumPlayer())
call SetPlayerAbilityAvailableBJ(false, 'A012', GetEnumPlayer())   // Taunt
call SetPlayerAbilityAvailableBJ(false, 'A03B', GetEnumPlayer())   // Rally Up
call IssueImmediateOrderBJ(gg_unit_h04M_1461, "berserk")           // = Open Gate, on two named gates
call IssueImmediateOrderBJ(gg_unit_h04M_1462, "berserk")
```

An AI faction therefore **cannot ever close a gate it owns**, and two specific
gates are force-opened at boot. AI-held gates are permanently open, so an AI
army never has to open one to leave and never blocks a neighbour with one.
Enemy gates are just units, so an attack-move destroys them without special
handling. The same disable list also removes Defend, Taunt and the map-wide
"Rally Up" ability from the AI — the last of which is a *human* advantage
retained deliberately (`AbilityRallyUp` enumerates all your units map-wide and
orders them to a point).

The map ships **no wall or gate destructables at all** (21 destructable
overrides, all trees, rocks and line-of-sight blockers). There is nothing an
army can be stopped by that is not a unit it can simply kill.

## 4. Does it cheat? Honest ledger

**Yes, in three places, and they are worth naming precisely because they are
narrow.** Every item below is gated on `GetPlayerController(...) ==
MAP_CONTROL_COMPUTER` and applies to no human.

| Cheat | Magnitude | Where | Assessment |
|---|---|---|---|
| **Recurring lumber subsidy** | **+250 lumber every 45 s**, plus +25 gold | `AIWarPeace` head, `war3map.j:25461–25462`, gated by `Func001C` (slot PLAYING **and** `MAP_CONTROL_COMPUTER`) | **The big one.** Units cost 3–20 lumber, so this is 12–80 units' worth of wood per tick, forever. The +25 gold is trivial against 18–213 territory income. |
| **Free movement speed + a higher cap** | All players capped at `R00U` level 6 (`:7560`, applied to `GetPlayersAll()`); AI **granted level 6 free and capped at 9** (`:23970–23971`) | `R00U` "Extra Speed for AI1" (`rmvx`, base 5 / mod 10) | AI armies start at the human's maximum speed without paying, and can exceed it. A *mobility* cheat that directly offsets the AI's lack of route planning. |
| **Hero XP handicap** | **250%** for AI kingdoms (`:23982`), 150% for Player 15 (`:24346`), **500%** for the Viking (`:35186`) | `SetPlayerHandicapXPBJ` | Compensates for the AI having no hero policy at all (§2.7). |
| Per-faction starting gold | +100…+300 once, faction-specific, some on a 1-in-7 roll | `Trig_SetupAI_Actions` | Scenario balancing, one-shot. |
| Starting debit | −25 gold, −150 lumber to every AI (`:23960`) | same | Partially offsets the above. |

**What is *not* cheated**, checked and confirmed:

- **Vision.** `SetupStartingVisibility` gives *every* player — human and AI —
  a 10,000–14,500 radius reveal around their capital for 3 seconds at start,
  then stops it. There are no AI-only fog modifiers, no `FogEnable`, no
  cheat-vision alliances. **NEGATIVE SEARCH: no AI vision advantage found.**
- **Gold income.** Symmetric (§3.3).
- **Spawned reinforcements for the kingdom AIs.** The scripted armies
  (`RaidersIrish`, `RaidersFrankish`, `VikingHeathenArmy`) belong to
  Players 16 and 6, both of which are **explicitly removed** from
  `PG_Kingdoms_AI`. They are scenario events that pressure everyone, not
  top-ups for the AI kingdoms. The Viking invasion *is* a spawned army
  (+500 gold, +1000 lumber, ~85 units, a level-25 pre-skilled hero) but it is
  a scripted world event that the human faces too.
- **Omniscient enumeration.** The map script never enumerates enemy units on
  the AI's behalf.

**The honest caveat**: `GetEnemyBase()` / `GetEnemyExpansion()` are Blizzard
natives. Whether *they* respect fog is not determinable from this artifact.
**UNKNOWN** — and it is the same unknown that applies to any engine-`.ai`
design, including ours if we ever hand off to captains.

**Verdict on "runs quite well"**: it is *not* simply a resource cheat. The
subsidy is real and large in lumber, but it is targeted at exactly the
subsystem the script cannot run (worker economy, §2.6) rather than at combat
power. The competence the owner observed comes mostly from §3.5, §3.6 and
§2.3 — the map's removal of hard cases, and total commitment.

## 5. How it handles the five things that break ours

| Our failure | Brytenwalda's answer | Class |
|---|---|---|
| **Armies that do not commit fully** | Not representable. `min = max = all` for every unit type; one wave; no reserve. | Design elimination |
| **Armies that pile at chokepoints** | `FormGroup(3, true)` gathers the army *before* it moves, so it arrives as a body rather than trickling into a choke. `SetRandomPaths(false)` keeps it on the direct route. Beyond that: nothing — and the map has no gates or walls that can hold a choke, because AI gates cannot close and no wall destructables exist. | Mixed: one real mechanism (`FormGroup`) + design elimination |
| **Armies that walk to walls they cannot break** | Cannot happen. There is no impassable enemy structure: gates are killable units, the AI cannot close its own, and there are no destructable walls anywhere in the map. | Design elimination |
| **Factions that never leave home** | The war gate and the attack gate share the same constant (**FoodUsed 25**), so a faction only enters a war it can immediately prosecute; and `TownThreatened()` is the *only* thing that keeps an army home. | Real mechanism — cheap and effective |
| **Allied AIs blocking each other** | `SetAllianceTarget(target)` publishes the chosen target to the alliance so allies converge rather than diverge; `SetDefendPlayer(false)` stops them chasing each other's defence; the diplomacy layer keeps vassals' wars identical to their overlord's. | Real mechanism (engine-provided) |
| **When an attack fails** | `CaptainRetreating()` blocks the next wave until the engine finishes retreating, then it re-forms and re-targets from scratch. No memory, no blacklist, no write-off. | Weak — see §7 |
| **Water crossings** | A tech-gated waygate pair; no transport model. | Design elimination |

## 6. What it does that we do not

1. **A shared threshold constant across the strategic and tactical layers.**
   FoodUsed 25 gates both "may declare war" and "may attack". Objective
   selection cannot outrun execution capability. We score six goals every tick
   with no equivalent guarantee that the chosen goal is *executable now*.
2. **`FormGroup` before moving.** A muster phase is a first-class step, not an
   emergent consequence. Our army leaves as it is.
3. **One order per wave.** The engine captain owns movement; the AI owns
   decisions. Our order economy is the thing we have had to defend against
   repeatedly.
4. **`SetAllianceTarget` for ally coordination.** A published claim, one line,
   engine-enforced. Our shared claim ledger is far richer and has still
   produced allied interference.
5. **One script, 19 factions, differentiated by upgrade-gated booleans.**
6. **Diplomacy as the strategic layer.** The AI's "objective" is *whom it is at
   war with*, decided on a slow 45 s clock with hysteresis, while target
   *selection* is delegated. Two clocks, cleanly separated — slow intent, fast
   execution.
7. **A negotiation surface.** `CM_NeutralAI` lets the human bribe, threaten and
   make peace with the AI. Much of a computer opponent's felt intelligence
   comes from being *answerable*, not from pathing.

## 7. What it deliberately does not attempt — the real lesson

The list of things Brytenwalda's AI does not do is longer than the list of
things it does, and almost every omission was **paid for by a map-design
decision** rather than left as a gap:

| Not attempted | How the map pays for it |
|---|---|
| Building placement | Pre-placed plots that upgrade in place (§3.5) |
| Base expansion | `BuildExpansion` exists and is never called; territory is captured, not expanded into |
| Gold economy | Territory income, symmetric (§3.3) |
| Naval transport | One tech-gated waygate pair (§3.4) |
| Gate management | AI's Close Gate ability removed (§3.6) |
| Route planning / chokepoints | Nothing — plus a free +55 movement speed so bad routes cost less (§4) |
| Hero selection & skills | Empty functions; a hard-coded skill in `AILevelUp` and scripted named heroes |
| Partial commitment / garrisons | `TownThreatened()` binary; total commitment otherwise |
| Target valuation | Delegated to `GetEnemyBase()` / `GetEnemyExpansion()` |
| Failure memory | None; `CaptainRetreating()` only |
| Difficulty levels | None — one script, one behaviour |

**This is the finding.** Brytenwalda confirms, on a large real-geography map,
the strongest conclusion of our prior research: *the maps with good computer
opponents got there by making the hard part unnecessary, not by solving it.*
Its AI is roughly 120 lines of decision logic. What makes it work is 2,980
hand-placed units, a hand-drawn 49-edge neighbour graph, a plot-upgrade build
system, and a gate ability deliberately withheld.

It also means **our prior brief's "competence UNKNOWN" should now read
"competent, and cheaply so — but not transferable as an AI."** Brytenwalda does
not demonstrate a WC3 AI that reasons about geography. It demonstrates a map
built so that an AI need not.

## 8. Ranked list of what rome-ai should steal

Ordered by expected value against our named playtest failures. Nothing here
requires abandoning our architecture; items 1–4 are small.

1. **Tie objective selection to execution capability with a shared constant.**
   *Fixes: factions that never leave home; armies that do not commit fully.*
   Brytenwalda's war gate and attack gate are the same number. Our six goal
   scorers should not be able to select an objective the executor cannot start
   this tick: make the executor's own precondition (force present, route known,
   prerequisite held) a hard *filter* upstream of scoring, not a term inside
   it. This is one shared threshold, not a new subsystem.

2. **Add an explicit MUSTER phase before ROUTE.** *Fixes: armies that pile at
   chokepoints; armies that do not commit fully.* `FormGroup(3, true)` is one
   call and it is the reason Brytenwalda's armies arrive as a body. Our mission
   executor already has phases; insert muster-at-staging-point with a
   completion predicate (N% of the committed force within R of the staging
   point, or a timeout) before the army is allowed to move. An army that
   trickles into a choke dies in detail; one that arrives together does not.

3. **Publish the objective to allies as a single claim, and honour it.**
   *Fixes: allied AIs blocking each other.* `SetAllianceTarget` is one line and
   is why Brytenwalda's allies converge. Our claim ledger is richer and still
   produces interference — the lesson is that the *simplest possible* shared
   fact (one target per alliance) beats a detailed ledger nobody defers to.
   Consider collapsing to a single published objective per alliance and making
   deference the default rather than a negotiated outcome.

4. **Make the "home is threatened" check preemptive and binary at the top of
   the attack loop.** *Fixes: armies that do not commit fully.* Our DEFEND/
   RETREAT preemption is a scored goal competing with others. Brytenwalda's
   `TownThreatened()` short-circuits before any targeting happens. A binary
   pre-gate is not a substitute for our split-and-recall logic, but it is a
   cheap guarantee that an army under home pressure never *starts* a new
   commitment — which is a different and simpler property than the one our
   write-off term provides.

5. **Two clocks, cleanly separated: slow intent, fast execution.** *Fixes:
   armies that do not commit fully.* Brytenwalda decides *whom to fight* every
   45 s with explicit hysteresis (recent-peace memory, 1-in-5 and 1-in-6
   rolls), and *where to walk* on a 2 s loop. Our posture layer already gestures
   at this; making the strategic re-decision genuinely infrequent — and its
   memory explicit — is more robust than incumbency bonuses and dwell timers on
   a single fast loop.

6. **Consider tech-gated crossings instead of transport logic for future
   maps.** *Fixes: armies that walk to walls they cannot break; naval.* Our
   naval transport works and should stay for Fall of Rome. But the waygate
   pattern is the right default for *our own* maps: it converts an amphibious
   planning problem into a graph edge and a research, costs two units, and
   still reads to the player as a strategic milestone.

7. **Withhold abilities the AI cannot use well.** *Fixes: armies that walk to
   walls they cannot break.* Brytenwalda removes Close Gate, Defend, Taunt and
   Rally Up from AI players. We already ship an equivalence for gate toggling
   (DESIGN.md §8.3) — the stronger move is to reduce the AI's *action space* to
   what it demonstrably handles, disclose that as a design choice, and stop
   paying for coverage of verbs it uses badly.

8. **Adopt "one script, N factions, differentiated by data-driven booleans."**
   Not a failure fix — a maintenance win. Brytenwalda's 40 `gCond_*` flags give
   19 distinct faction behaviours from one file. Our twelve-faction
   differentiation should be table-driven for the same reason.

## 9. What we should *not* copy

- **Total commitment.** `min = max = all` works for Brytenwalda because there
  are no walls, no chokepoints that hold, no timer, and settlements are not
  instantly flippable. Fall of Rome has a 30-minute deadline, a 100-food cap,
  capitals that flip below 500 HP and flip straight back. An always-everything
  army is exactly the behaviour that loses a held capital to a two-unit
  counter-raid. Our split-and-recall logic is *correct for our map* and should
  stay.
- **Uniform-random target selection.** Drawing the war target uniformly from
  neighbours is why Brytenwalda's factions are strategically inert — they never
  press a weak neighbour or exploit a collapse. Against a strong human this is
  the AI's biggest weakness, and it is exactly the thing our six scorers exist
  to do better.
- **The lumber subsidy.** It is a real cheat, it is large, and our
  `AI_HANDICAP` default of 1.0 is the better position. If we ever want the
  *effect*, buy it honestly: Brytenwalda's subsidy exists only because its
  script cannot run a worker economy.
- **The free movement-speed upgrade.** This is the most tempting cheat in the
  file — it papers over bad routing — and for that reason the most dishonest.
  It would silently mask exactly the failure we are trying to fix.
- **No failure memory.** `CaptainRetreating()` and nothing else means
  Brytenwalda will re-throw the same army at the same target indefinitely. Our
  write-off term and progress-abort conditions are strictly better; do not
  trade them away for simplicity.
- **Empty hero handling.** Fine for a map where heroes are scenery; not fine
  for ours.

## 10. Corrections to prior research

- `brief-04-amai.md` §9 records Brytenwalda's competence as **UNKNOWN** on the
  basis that no source was located. Source located; competence is now
  **CODE-INFERRED + EXPERIMENTAL (owner playtest)**, and the row should read:
  *competent, via design elimination rather than AI capability.*
- The same section reads the changelog entry "Irish factions failing to invade
  the mainland" as "evidence of geography-aware authoring". That is correct but
  understated in an important way: the fix was a **waygate plus two graph
  edges**, i.e. evidence of geography-aware *map* authoring, not of an AI that
  reasons about water.
- `wc3-map-ai-decompositions.md` finds that essentially nobody drives the
  engine `.ai` subsystem (1.55% of a 5,350-map archive sample; 0 of the top 70
  live maps). Brytenwalda is a **confirmed positive**, on a non-melee
  (`isMeleeMap:false`) w3i v31 map with 19 AI factions — and the mechanism by
  which it clears the controller blocker is instructive: it does not convert
  slots at runtime at all, it declares them User and lets the host set Computer
  in the lobby.
